# Product

## Platform

web

## Users

Researchers who work with optical fibre sensors and need to analyse a test
after it is over:

- **FBG data**: the Bragg wavelength of each channel over time, exported by an
  interrogator (catman `.ASC`, `.txt`, `.csv`).
- **Optical spectra**: from an OSA or a UV-VIS-NIR spectrometer (OceanView
  exports, such as lossy-mode-resonance transmission), often hundreds of
  spectra per test.

Today that is the author, a master's student at UTFPR (CPGEI / NUEM), and
colleagues in the group. Researchers outside the group who install BraggFlow
from GitHub are an intended audience of the web interface itself, not only of
the Python package.

Their jobs:

- turn raw equipment exports into processed signals they can trust;
- mark the events of a test and measure each interval;
- follow a resonance, valley or peak, across a series of spectra;
- produce figures sized for journals (IEEE, Elsevier) and slides.

Python users of the package (`braggflow process`, the fluent
`OpticalPipeline` API) are a second audience, for scripting.

## Product Purpose

BraggFlow takes a test from the raw export to numbers and figures for a
dissertation or paper in one tool. Without it, the same work is spread over:

- Origin or Excel, by hand;
- MATLAB or Python scripts written again for each test;
- the equipment software (catman, OceanView).

Success means getting from the raw file to a publication figure, with values
that can be traced back and reproduced, without leaving the tool.

## Positioning

- **One recipe for every interface.** The web app and the command line share
  the same pipeline (`braggflow.recipe`). The same input gives the same output
  in either.
- **Traceable.** Every processed CSV carries units in its header and a JSON
  record of how it was produced. A project saves the whole analysis and reopens
  it in the same state: files, per-file settings, markers, evolution and figure
  style.
- **Built for this domain.** BraggFlow knows things that generic plotting tools
  do not:
  - interrogator artefacts and file concatenation;
  - Δλ and temperature compensation with each FBG's own thermal sensitivity;
  - transmission from sample, source and dark spectra;
  - acquisition times from spectrometer headers and file names;
  - tracking a valley across files from a reference wavelength.

  Equipment software, for its part, does not make cross-file analysis or
  publication figures.

## Operating Context

- **When and where.** Used after the test, on files already recorded, at a desk
  in the office or at home. It does not acquire data live from instruments.
- **Runs locally.** `braggflow-web` serves a Flask app on 127.0.0.1. One data
  folder (`data/`, `--data-dir` or `BRAGGFLOW_DATA_DIR`) holds:
  - raw files and uploads;
  - processed CSVs, one folder per project;
  - saved sensor setups, figure styles and projects.

  The page loads Plotly from a CDN.
- **Organised in projects.** The project saves itself and has undo and redo.
- **Inputs:**
  - interrogator exports, sometimes several files of one test joined in time
    order;
  - OSA spectra;
  - OceanView/SpectraSuite exports, with or without header;
  - raw sample, source and dark spectra;
  - whole folders of spectra from one test.
- **Outputs:**
  - processed CSV with JSON provenance;
  - CSV tables (interval statistics, peaks and valleys, evolution between
    spectra);
  - figures as PDF, PNG, SVG, EPS or TIFF at journal sizes;
  - PNG on the clipboard for slides.

## Capabilities and Constraints

- **Three tabs:**
  - *Séries temporais*: processing steps, plot per channel or overlaid,
    measuring a stretch, markers and interval statistics.
  - *Espectros*: one preparation for every spectrum or one per file,
    transmission from raw data, peaks and valleys, and the evolution of a
    valley between files, with a reference wavelength and events.
  - *Figura*: publication figures from processed CSVs, spectra or the
    evolution.
- **Front end.** Plain ES modules with no build step. Plotly draws the
  interactive plots. matplotlib renders the publication figures on the server.
- **Language.** The interface is bilingual, Brazilian Portuguese and English,
  with a switch. Researchers outside the group must be able to work in English.
  Code identifiers and the documentation are in English. Everything that goes
  into a paper (figure labels, automatic legends) follows the language chosen
  for the figure.
- **Domain terms the interface uses:** λ, Δλ, FWHM, K_T, LMR, interrogador,
  espectro, vale and pico, evolução, marcação and evento.
- **Data confidentiality.** Experimental data from funded projects may be
  confidential. Real experimental data never goes into the repository; examples
  and tests use synthetic data generated by script (`examples/`,
  `tests/lmr_synthetic.py`).
- **Tests.** CI runs pytest and Playwright browser tests on Ubuntu and Windows,
  Python 3.10–3.14.
- **Package.** Python ≥ 3.10, MIT licence.

## Product Principles

1. **Traceable by default.** A number that goes into a paper must be
   reproducible from the raw file, through the provenance JSON and the saved
   project.
2. **From raw file to figure in one place.** Cover the common path that
   otherwise needs Origin, scripts and the equipment software.
3. **Speak the lab's language.** Use the domain's terms and handle the quirks
   of real equipment exports, instead of asking the user to clean files first.
4. **Scale to real tests.** Expect hundreds of spectra and long series: batch
   operations, caching, and one bad file never stops the analysis.
5. **Real data stays with the user.** Only synthetic data in the repository,
   docs and tests.
